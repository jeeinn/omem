# 参考项目：组件复用、许可证风险与可借鉴代码清单

> **归档**（2026-10-26）：调查已结束，结论是不把这些项目引进运行时依赖。本文只留作记录，不再作为开工依据。
>
> 版本：v1.0 · 日期：2026-10-15 · 隶属：《跨 Agent 个人记忆与知识库产品规划》v0.4 第 10.2 节的配套细化
>
> 对象：memoir / lore / hstry / memofs 四个 MIT 开源项目
>
> 用途：Phase 0–3 自研时的复用决策依据。复用分三级——**A 直接依赖**（作为库引入）、**B 源码吸收**（复制改造，需署名）、**C 机制参考**（只学设计，代码自写）。

## 1. 总览

| 项目 | 语言/栈 | 许可证 | 规模/活跃度 | 复用价值定位 |
|---|---|---|---|---|
| [memoir](https://github.com/camgitt/memoir) | JavaScript / Node ≥18 | MIT | 14★，153 commits | 机制参考为主（C），安全工程范例 |
| [lore](https://github.com/DnaMes/lore) | Python 3.11+ / Flask / SQLite | MIT | 中等（25 个提取器） | 适配器层源码吸收（B） |
| [hstry](https://github.com/byteowlz/hstry) | Rust workspace + TS 适配器 | MIT | 46★，29 releases，活跃 | 浏览器扩展源码吸收（B），接口设计参考（C） |
| [memofs](https://github.com/memo-fs/memofs) | TypeScript / pnpm monorepo | MIT（代码） | 6★，435 commits，Beta | 个别 npm 包可直接依赖（A），目录结构与 Linter 机制参考（C） |

**总体结论**：四者均 MIT，许可证风险整体为低。真正的风险不在许可证，在**项目存活度**（除 hstry 外星数都很低，随时可能弃坑）——因此复用策略上：除 memofs 个别稳定接口包外，一律不作为运行时依赖引入，优先源码吸收（带署名）或机制自研，避免上游死亡拖垮核心。

## 2. memoir（camgitt/memoir）

**定位**：项目级便携 Markdown 记忆 + Codex↔Cursor 会话交接，MCP 工具集（`memoir_note/remember/read/recall/resume/forget`）。

### 2.1 组件复用清单

| 复用级别 | 组件 | 位置 | 说明 |
|---|---|---|---|
| C | `unverified` 记忆分层 | `src/`（MCP 写入路径） | 自动采集记录默认 `unverified`，确认后晋升——已并入主规划 5.2 条目格式 |
| C | `clean-decisions` 正则清理 | `src/` | 专清 LLM 误造的决策行——LLM 加工流水线的"事后纠错"必备机制 |
| C | `work setup/resume` 会话交接 | `src/`（测试见 `test-work-handoff.mjs`） | 目标/已答问题/决策/下一步/检查回执跨工具携带；台账存 gitignore 的 `.memoir/` |
| C | SessionStart hook 简报注入 | `src/` | ~300 token 预算的会话简报——与主规划 MEMORY-INDEX.md 被动注入同思路，其 token 控制实现可抄 |
| C | E2E 备份加密 | `src/`（`test-encryption.mjs`） | 口令 ≥12 字符、快照 manifest 逐文件认证、恢复时拒绝缺 blob/损坏/不安全路径/symlink——跨设备同步的加密参考 |
| C | 对抗性安全测试 | `test-work-adversarial.mjs`、`docs/HANDOFF-SECURITY-AUDIT.md` | 有公开安全审计与修复记录，其测试用例设计是本项目安全测试的模板 |
| C | 增量词法索引 | `docs/RETRIEVAL-INDEX.md`、`src/` | `recall` 的证据式返回（匹配段落+路径+行号+ID）——检索结果可信度设计值得学 |

### 2.2 许可证与风险

- **许可证**：MIT——风险低。若源码吸收其加密/索引实现，按 MIT 要求在 NOTICE 中保留其版权声明。
- **非代码依赖风险**：云端备份走 Supabase（`supabase/migrations/`）、`consolidate --smart` 调 Gemini API——均为可选服务非代码依赖，不影响复用；但**不要复用其云端协议**（账号加密备份是遗留格式，作者自己都在迁移）。
- **维护风险**：14★单人项目，随时停更——只做源码吸收，不依赖。
- **命名**：npm 包名 `memoir-cli` 已被占用，本项目取名需避开。

## 3. lore（DnaMes/lore）

**定位**：本地优先双工具——10+ AI 工具会话档案库 + 共享 Agent 记忆。Python 包结构：`lore/core`（数据模型）、`lore/extractors`（会话解析）、`lore/exporters`（Markdown/Context 导出）、`lore/interfaces`（CLI/Web/MCP 入口）。

### 3.1 组件复用清单

| 复用级别 | 组件 | 位置 | 说明 |
|---|---|---|---|
| **B（核心）** | 会话提取器 ×25 | `lore/extractors/` | **本清单最大单项价值**。成熟：Claude Code（`~/.claude/projects/` JSONL）、Cursor（SQLite 安全拷贝）、Codex、Gemini CLI、Aider（`.aider.chat.history.md`）、Warp、OpenCode、Copilot 等；国内起点：Kimi、Qwen Code 提取器已存在但**未经真实数据验证**——拿来当起点，必须用真实会话补回归测试 |
| B | 密钥脱敏正则库 | `lore/utils/redact.py` | OpenAI/Anthropic 密钥、JWT、PEM 的检测正则——直接吸收进隐私过滤模块（主规划 5.3.3） |
| C | SQLite schema（FTS + 会话摘要表） | `~/.lore/lore.sqlite` | FTS5 全文索引 + `session_summaries` 表设计，与主规划选型一致，schema 可对照参考 |
| C | MCP 11 工具契约 | `lore/interfaces/`（`lore-mcp`） | `search_history / memory_write / memory_recall / memory_feedback`——尤其 `memory_feedback`（用户对记忆打分）是主规划尚未设计的反馈闭环，值得纳入 |
| C | 会话切换器 | `lore_session_cli.py` | 限流时携最近 15 条消息切换到另一工具——非核心但低成本高感知的功能点 |
| C | 提取器安全模式 | `lore/extractors/` | Cursor/Hermes 一律读 SQLite **副本**而非原库（避免锁库/损坏）——适配器工程规范 |

### 3.2 许可证与风险

- **许可证**：MIT——25 个提取器全部可源码吸收。**注意**：本项目核心是 TypeScript 路线（主规划第 6 章倾向 TS），lore 是 Python——提取器逻辑可移植（文件解析逻辑语言无关），但需逐个重写为 TS；这反而符合"统一中间格式 + 适配器"的自研路线，lore 提取器当作**算法参考与测试用例来源**（其 fixture 数据可对照验证移植正确性）。
- **反义教训（必须执行）**：其 README 自曝 Cline/Roo/Kimi/Zed 等提取器"仅基于文档 schema fixtures、未经真实数据验证"——本项目适配器门槛（主规划 7.2）已规定"真实会话样本回归测试"，lore 的翻车是前车之鉴。
- **维护风险**：单人项目、Forgejo 自托管（非 GitHub 主流托管，社区可见性低）——同样只吸收不依赖。

## 4. hstry（byteowlz/hstry）

**定位**：Rust workspace 的统一 AI 聊天历史库。Crates：`hstry-core`（SQLite/配置/模型）、`hstry-runtime`（适配器执行）、`hstry-cli`、`hstry-tui`、`hstry-mcp`、`hstry-api`（axum 本地 ingest 服务器）；另有 `adapters/`（TS 适配器）、`extension/`（Chrome MV3）、`skills/hstry-search`。

### 4.1 组件复用清单

| 复用级别 | 组件 | 位置 | 说明 |
|---|---|---|---|
| **B（核心）** | Chrome MV3 浏览器扩展 | `extension/`（"hstry sync"） | 后台同步 ChatGPT/Claude/Gemini/Perplexity 网页对话，POST 到本地 API（token 认证）——**全领域采集的关键拼图**（主规划采集层③），整体源码吸收改造为本项目扩展 |
| B | 本地 ingest API 服务器 | `crates/hstry-api`（axum，127.0.0.1:41770，`/ingest`） | 浏览器扩展的接收端设计（本机回环 + token 认证）——若本项目用 TS，可参考其接口设计用 Fastify/Express 重写 |
| C | 适配器接口规范 | `adapters/`（TS 模块） | `detect(path)` + `parse(path, options)` 两函数接口，经 Bun/Deno/Node 加载——简洁，主规划适配器接口的直接参考；其 12 个本地适配器的默认路径表（`~/.claude/projects`、`~/.codex/sessions`、Cursor `workspaceStorage` 等）可整体搬用为初始路径配置 |
| C | 查询类型自动识别 | `crates/hstry-core` | 自然语言查询用 porter 词干化、代码查询保留下划线/点号/路径分隔符——FTS5 检索体验细节，低成本高收益 |
| C | 跨 agent 会话恢复 | `hstry resume` | Codex 会话在 Claude Code 中恢复（含格式转换）——与 lore 切换器同生态位，看主规划 Phase 4 是否纳入 |
| C | SSH 远程同步 | `hstry remote` | 跨设备轻量方案，与主规划 git 同步互补（在线查询远端库、无需完整 checkout）——列为 Phase 2 可选扩展 |
| C | 适配器版本锁定机制 | `hstry adapters update` | 适配器版本与二进制锁定、不匹配拒绝 sync——防止格式漂移静默失败，主规划适配器版本治理直接照抄该思路 |
| A | 检索技能分发 | `skills/hstry-search` | `hstry skill install` 把检索能力作为 agent skill 分发——印证主规划 Phase 4 技能库路径的可行性 |

### 4.2 许可证与风险

- **许可证**：MIT——扩展与适配器均可吸收。
- **技术栈错配**：核心是 Rust，本项目核心走 TS——**只吸收 `extension/` 与 `adapters/`（本来就是 TS）**，Rust 部分只学设计。
- **分发风险**：Chrome MV3 扩展"Load unpacked"开发者模式分发没问题，但若未来上 Chrome Web Store 需过审（读取 ChatGPT/Claude 页面 DOM 的权限审查趋严）——影响不大，自托管分发起步即可。
- **维护风险**：四者中最活跃（46★、29 releases），但仍是小项目——扩展代码吸收后需自维护。

| C | Session Outcomes 晋升机制 | `packages/core`（AgentFS） | 工作区草稿按 success/failure/aborted 结局决定哪些记忆晋升持久层——比 unverified 分层更细的记忆准入设计 |
| C | 契约测试方法 | `@memofs/testing`、`@memofs/spec` | JSON schema 契约 + mock + fixture 的测试组织方式——统一中间格式的测试体系参考 |
| ⚠️ 明确不复用 | `@memofs/spec` 格式本身 | — | **警示**：若沿用其 schema，数据格式即与 memofs 生态耦合，损害"Markdown 自主事实源"的根本决策——schema 必须自定义 |

### 5.2 许可证与风险

- **许可证**：代码 MIT，风险低。但**商业模式是 open-core**（托管同步/团队空间/托管 MCP 是付费云）——需持续关注两点：① 后续新增包可能改用非 MIT 许可（open-core 项目常见操作），引入依赖前逐包核对 LICENSE 文件；② 它是四者中与本产品定位最重叠的竞品，**依赖其包 = 为竞品生态输血 + 被其 breaking change 卡脖子**——因此唯一直接依赖候选（adapter-transformers）也建议仅作为 fallback，首选裸 transformers.js。
- **Beta 状态**：6★、标记 Beta，API 稳定性无承诺——同前，不做运行时依赖。
- **借鉴边界**：目录结构、Linter、lineage 均为**机制层面的思想**，实现自写，无许可证义务。

## 6. 横向：许可证合规操作清单（自研 + 吸收混合模式）

1. **MIT 吸收义务**：源码吸收（B 级）时，在仓库根建立 `NOTICE` 或 `THIRD-PARTY-NOTICES` 文件，逐条注明"代码源自 <repo URL>，Copyright (c) <作者>，MIT License"并附许可证原文。C 级机制参考无义务。
2. **禁止事项**：不得沿用对方项目名/包名做命名或宣传（memoir-cli、lore、hstry、memofs 均是他人项目名）；MIT 无商标授权。
3. **专利**：MIT 不含明确专利授权（区别于 Apache-2.0）——四家均为个人/小团队项目、专利风险实际极低，但正式发布前可在 NOTICE 中声明吸收范围。
4. **传递依赖**：吸收 lore 的 redact 正则、hstry 的扩展代码时，检查其自身依赖的第三方库许可（如扩展里的打包库）一并登记。
5. **本项目反向义务**：本项目最终 MIT 开源（主规划 7.1/7.2），与吸收 MIT 代码完全兼容，无污染问题。
6. **吸收台账**：在仓库内维护 `docs/absorbed-code.md`，每笔吸收记录：来源、commit hash、吸收日期、改动范围——既满足合规追溯，也方便上游出 CVE/bugfix 时回查。
