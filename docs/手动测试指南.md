# omem V0.1 手动测试指南

> 目标读者：开发者本人（V0.1 用户群边界见评估报告 4.9）。
> 全部命令在 `X:/omem` 项目根执行；文中 `node bin/omem.js` 可替换为全局命令 `omem`（见 §1 路径 B）。

---

## 1. 测试路径决策：打包 vs 直接跑

| 路径 | 命令 | 适用场景 | 说明 |
|---|---|---|---|
| **A. 项目内直接跑**（日常主用） | `npm run build` 后 `node bin/omem.js <cmd>` | 开发循环、改完即测 | bin 包装器自动注入 `--experimental-sqlite`，无需手动带 flag |
| **B. npm link** | `npm link` → 任意目录执行 `omem <cmd>` | 验证"全局安装后"的真实体验 | 同时验证 npm bin shim + flag 自注入 + `files` 字段；`npm unlink omem -g` 撤销 |
| **C. npm pack 打 tarball** | `npm pack` → `npm install -g omem-0.1.0.tgz` | 发布前产物验证 | 验证 tarball 内容完整性（dist/bin 是否打进）；`prepublishOnly` 会先自动 build |
| **D. 自动化套件** | `npm test`（Vitest 136 例）/ `npm run smoke`（bash 冒烟 46 项） | 每次改动的回归底线 | 冒烟含 MCP 裸 JSON-RPC 探针与 stdout 纯净断言 |

**建议节奏**：改动用 A 快速迭代 → 提交前跑 D 全量 → 每个里程碑用 B/C 做一次"干净环境"验证。

环境要求：Node ≥ 22.5（`node:sqlite` 内建 FTS5）。检查：`node --version`。

## 2. 铁律：隔离 OMEM_HOME

omem 的数据目录由 `OMEM_HOME` 决定（默认 `~/.omem`）。**测试一律指向一次性目录**，不要直接拿真实 `~/.omem` 做实验：

```bash
# Git Bash
export OMEM_HOME=/tmp/omem-t1

# PowerShell
$env:OMEM_HOME="C:\Users\wei\omem-t1"
```

- `omem init` 会在 OMEM_HOME 建 git 数据仓；删目录即完全重置，无残留。
- 采集是**只读**的：`omem run` 只读 `~/.claude/projects`，不改会话文件；可用 `OMEM_CLAUDE_PROJECTS=<dir>` 指向合成 fixture。
- 用完即删：`rm -rf $OMEM_HOME`（Git Bash）或 `Remove-Item -Recurse`（PowerShell）。

## 3. 十五分钟冒烟脚本（按序执行）

每步给出预期。任一步不符，先看 §6 排障。

```bash
export OMEM_HOME=/tmp/omem-t1 && cd /x/omem

# S1 建库（--no-scan 跳过首次会话扫描，快；去掉则扫真实 ~/.claude/projects）
node bin/omem.js init --no-scan
# 预期：打印数据目录路径 + "git 数据仓已初始化"；退出码 0
# 产物：$OMEM_HOME/{knowledge,archive,index,snapshots,logs,config.toml,MEMORY-INDEX.md}

# S2 手动写入两条（一 fact 一 preference）
node bin/omem.js add "omem 的检索走 FTS5 trigram，中文查询词少于 3 个字符时退化为 LIKE 兜底" --type fact --domain tech --tags 检索,FTS5
node bin/omem.js add "以后部署统一用 Docker Compose，不再裸跑 docker run" --type preference --domain ops
# 预期：各打印 "已保存 id: YYYY-MM-DD-xxxxxx" + 文件路径；退出码 0

# S3 检索三形态
node bin/omem.js search "trigram 检索"   # 多词整串 → trigram MATCH（AND 语义）
node bin/omem.js search "部署"            # 2 字中文 → LIKE 兜底路径
node bin/omem.js search "不存在的词xyz"   # 无命中：提示"未找到"，不算错误（退出码 0）
# 预期：命中条目附 "——刚刚确认" 时效标注 + 免责框架结尾行

# S4 队列与生命周期
node bin/omem.js review     # 预期：队列为空（手动 add 的都是 verified）
node bin/omem.js gc         # 预期：扫描 active N 条（阈值 180 天），标记 stale 0 条

# S5 加工会话（合成 fixture，不碰真实数据）
OMEM_CLAUDE_PROJECTS=/x/omem/tests/fixtures/claude-projects node bin/omem.js run --dry-run
# 预期：打印 会话/消息/候选 计数；dry-run 不落盘
# 真跑一遍（落盘）后应看到：密钥 sk-ant-***REDACTED*** 已脱敏、sidechain/summary 已过滤

# S6 上下文导出与可观测
node bin/omem.js context --for plain    # 预期：打印 MEMORY-INDEX + 条目摘要
node bin/omem.js audit --tail 3         # 预期：JSONL 使用日志（add/search 事件）

# S7 同步状态
node bin/omem.js sync status
# 预期：后端 git / 远端未配置 / 待推送 0 · 未提交改动 N（init 的提交除外）
```

### 退出码契约（规格 §7）

| 码 | 含义 | 复现 |
|---|---|---|
| 0 | 成功（含"冲突已处理"） | 上述全部命令 |
| 1 | 用法错误 | `node bin/omem.js redact`（缺 --id） |
| 2 | 后端不可用 / 策略拒绝 | `omem profile use work` 后 `omem context --for plain` |

## 4. 分主题深测

### 4.1 md 权威性（第一卖点，优先验证）

```bash
rm -f $OMEM_HOME/index/omem.db*          # 索引全删
node bin/omem.js search "trigram"         # 预期：仍能检索（catch-up 重建）
node bin/omem.js rebuild                  # 预期：从 md 全量重建，条目数不变
cd $OMEM_HOME && git log --oneline | head # 预期：每条记忆的变更都是一次提交
```

再用 Obsidian/VSCode 打开 `$OMEM_HOME/knowledge` 改一条 md 的正文 → 跑 `omem search` → 改动生效（"下次访问检出"一致性协议）。

### 4.2 检索矩阵

| 查询 | 路径 | 预期 |
|---|---|---|
| `trigram 检索`（多词，各 ≥3 字符） | trigram MATCH | AND 语义，两条都出现才命中 |
| `部署`（2 字中文） | LIKE 兜底 | 子串匹配 |
| `Compose 部署`（整串无完全匹配） | 逐词 AND 重试 | 两词都出现的条目才返回 |
| `search "部署" --domain ops` | 过滤 | 只返回 ops 域 |
| stale 降权 | 两条路径都有 | 手工把某条 `last_confirmed` 改到 200 天前 + `omem gc` → 该条排后且带 stale 标注 |

### 4.3 同步（本地 bare remote，不碰公网）

```bash
git init --bare -b main /tmp/omem-remote.git
node bin/omem.js sync remote /tmp/omem-remote.git
node bin/omem.js add "同步测试条目" && node bin/omem.js sync     # push
git clone /tmp/omem-remote.git /tmp/omem-home2                  # 第二台"机器"
# 两边各 add 一条同名冲突内容后各自 sync → 预期：报告 conflicts，
# 远端版另存 <file>.conflict.md，本地版保留（只报告，不自动合并）
```

### 4.4 MCP 接线（真实使用路径）

```bash
# 1) 只读预览将写入的配置（不落盘、不备份——已修复的契约）
node bin/omem.js install --print-config workbuddy

# 2) 探针自检（合成会话走完整 JSON-RPC：握手 + tools list + 4 次调用 + stdout 纯净）
node tests/mcp-probe.mjs

# 3) 真实接线（会 merge 写入 ~/.workbuddy/mcp.json，写前自动备份；
#    同时在 ~/.claude/CLAUDE.md 写 marker 指令段，幂等替换）
cp ~/.workbuddy/mcp.json ~/.workbuddy/mcp.json.mybackup   # 自己再备一份
node bin/omem.js install --target workbuddy

# 4) 重启 WorkBuddy → 新对话中验证：让 agent"检索一下我的 omem 记忆"
```

注意：新 MCP 服务**不会自动激活**，必须重启客户端；交互会话与自动化会话的连接器开关相互独立。

### 4.5 安全基线

```bash
node bin/omem.js add "测试密钥 sk-ant-abc123 不要外泄" --type fact
grep -r "sk-ant-abc123" $OMEM_HOME/knowledge    # 预期：无命中（已打码）
grep -r "REDACTED" $OMEM_HOME/knowledge         # 预期：有打码标记

node bin/omem.js profile use work
node bin/omem.js context --for plain            # 预期：被拒，退出码 2（公司设备合规）
OMEM_ALLOW_WORK_EXPORT=1 node bin/omem.js context --for plain   # 显式放行

node bin/omem.js pause && node bin/omem.js resume   # 一键停/恢复采集
```

## 5. 已知边界（不是缺陷）

- Node < 22.5 无 `node:sqlite`，bin 包装器会给出启动失败提示。
- FTS5 trigram 对 <3 字符查询无效 → 走 LIKE 兜底，这是设计内行为（spike 结论）。
- `omem context` 在 work profile 下默认被拦，是合规设计，不是 bug。
- WebDAV/本地目录同步后端、时间衰减在 V0.2；`omem sync use webdav` 会提示不可用（退出码 2）。
- 档 0 规则抽取的质量（误报/漏报）未经真实数据系统评估——见 §3-S5 与 Q1 实验设计。

## 6. 排障速查

| 现象 | 大概率原因 |
|---|---|
| `ERR_UNSUPPORTED_ESM_URL_SCHEME` | 直接 `node dist/cli.js` 且漏了 `--experimental-sqlite`；用 `node bin/omem.js` |
| "未初始化：... 不存在" | 漏了 `export OMEM_HOME=...` 或目录被删；`omem init` 重建 |
| 检索结果为空但明明 add 过 | 查询词 <3 字符且无子串匹配；试更长的词或 `--all` |
| `omem install` 后客户端不显示工具 | 未重启客户端；或连接器开关被关（左下角加号 → 连接器管理） |
| push 失败 | 无远端或网络；`omem sync status` 看 ahead/behind，本地提交不丢 |
