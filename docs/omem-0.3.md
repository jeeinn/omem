omem v0.3 产品设计评审
这次我会采用一次正式的架构评审方式，而不是简单地给你列功能建议。

先明确评审原则：

不以功能数量为目标，而以最小责任边界为目标。

我们希望最终得到一个系统：
- 没有大模型 API 也能正常工作。
- 没有数据库也能正常工作。
- 更换 Agent 不需要迁移记忆。
- Agent 犯错时，用户能够纠正。
- 记忆越来越多时，不需要无限增加基础设施。
- 最重要的是，系统不会因为自动化而悄悄改变用户的真实记忆。

而不是由 omem 自己运行一个完整的 LLM 记忆提取流水线。

我认为当前存在三个问题
问题 A：Agent 的提取行为缺少一致性约束。

不同 Agent 可能生成完全不同的记忆。

例如：

用户说：
我现在主要使用 PHP，但最近在学习 Rust。

Agent A 可能生成：
用户是 PHP 程序员，正在学习 Rust。


Agent B 可能生成：
用户的主要技术栈是 PHP、Rust。


Agent C 可能生成：
用户正在从 PHP 转向 Rust。


这三个结论的含义完全不同。

尤其是第三个，甚至可能是模型自己推断出来的。

因此，我建议 omem 不负责规定如何提取，但需要规定什么样的内容可以写入。

例如，给 Agent 一套非常简单的写入原则：
- 明确区分事实、偏好、计划、推断。
- 计划不能直接当成已经发生的事实。
- 不确定的信息不能写成确定性结论。
- 必须尽量保留用户表达的原始语义。
- 重要结论必须携带原始会话证据。
这些规则放在 PROCESS.md 和 MCP instructions 中，而不是写进一套复杂的提取引擎。

问题 B：PROCESS.md 是一个工作清单，不应该成为记忆系统的核心。

目前它承担了待处理会话、项目分组、Topic 词表等功能。

这是合理的，但要注意：

PROCESS.md 应该是一个可以随时重建的任务视图，而不是第二套记忆数据库。

如果 Agent 已经处理了一条会话，omem 应该能够根据可验证的处理状态更新清单，而不是依赖 Agent 自己记住处理进度。

你目前通过写入后重新生成 PROCESS.md，已经解决了部分问题。

但是，我发现一个值得重新审视的问题
当前的 Topic 身份模型，实际上把多个不同概念合并了。

例如：

这里的 php 既是文件名，也是记忆的唯一身份。

最后：

这三个版本实际上不是简单的覆盖关系。

它们分别表达：
1. 当前技术栈。
2. 技术栈发生变化。
3. 两种技术栈并存于不同场景。
Git 能保存三个版本，却不能告诉 Agent 哪个版本代表当前事实。

不过，我不建议因此重新引入复杂的 ID 和 supersedes 状态机。

我建议继续使用 Topic 作为文件身份，但是要区分：
- Topic：文档的身份。
- Revision：文档的版本。
- Content：当前有效内容。
- Evidence：支持当前内容的证据。
Git 已经承担 Revision 的主要职责，不必再造一套版本数据库。

真正需要完善的是写入协议，而不是存储模型。
还有一个更严重的问题：证据继承
我仔细看了你的架构说明。

当前同 Topic 更新时：
- 正文整篇覆盖。
- created 保留。
- source_sessions 和 evidence 累积。
- confirmations 和 last_confirmed 保留。
- confidence 根据本次写入重新计算。
这套设计在实现层面很简洁，但在语义上存在风险。
GitHub


举个例子：

旧记忆：
用户主要使用 PHP 开发。


旧证据：
session-001
用户：我一直使用 PHP 开发。


新记忆：
用户目前主要使用 Rust 开发。


如果旧证据直接继承，那么证据和新正文就不再对应。

更麻烦的是，如果新内容没有提供有效证据，旧证据可能让它看起来仍然有较高可信度。

这就是一个典型的证据污染问题。

我的建议是：
1. 更新正文时，重新计算当前正文的证据。
2. 只有明确仍然支持新内容的旧证据才能继承。
3. 不支持新内容的旧证据仍然留在 Git 历史中，但不能继续参与当前置信度计算。
4. 不要把旧内容被人工看过，等同于新内容也被人工看过。
这里不需要实现 Claim 级知识图谱。先把文档级证据边界做对就行。

首先，我们需要纠正一个认知：

记忆检索不等于向量检索。

检索的本质是：

给定一个问题，找到能够帮助回答这个问题的历史信息。

向量检索只是其中一种实现方法。

- stale 仍然可检索，但权重降低。
- archived 不参与默认检索。
- 会话检索只搜索用户发言证据域。
这些约束我认为是合理的。

4. Memory Update：记忆更新与冲突处理
omem 实现写入保护
Agent 判断语义变化

这是整个五个环节中，我认为最需要认真设计的地方。

而且我想纠正上次回答中的一个倾向：不能简单地给 save_memory 增加 CREATE、UPDATE、APPEND、CONTRADICT 四种操作，就认为问题解决了。

因为这些操作本身也需要理解语义。

例如：

用户说：
我不再使用 PHP 了，现在主要写 Rust。

这是 UPDATE。

用户说：
我还在使用 PHP，但新项目使用 Rust。

这是 APPEND。

用户说：
我从来没有说过我喜欢 PHP。

这是 CONTRADICT，甚至可能是对旧记忆的纠错。

判断这几种语义，应该交给 Agent，而不是 omem。
当前真正的问题是什么？
你现在的写入策略是：
save_memory(topic, content)
           ↓
       commitEntry
           ↓
     同 Topic 覆盖
           ↓
      写前 Snapshot
           ↓
        Git 历史


这很简单，但存在两个风险：
1. Agent 误判 Topic，覆盖了不应该覆盖的记忆。
2. 两个 Agent 同时更新同一个 Topic，后写入者可能覆盖前一个人的新内容。
Git 快照只能让你找回历史，不能防止错误发生。

我建议把更新机制分成三个层面。
第一层：写入意图
由 Agent 在调用 save_memory 前决定。

建议只提供三种基本意图：
操作	语义
create	创建一个新主题
replace	更新当前主题的完整内容
append	追加新的独立信息

contradict 不建议作为独立的存储操作。

因为冲突不是一种文件操作，而是一种语义关系。

Agent 发现冲突后，应该决定是修正、保留历史，还是请求用户澄清。
第二层：omem 写入保护
omem 不判断内容是否正确，但要防止不安全的写入。

我建议增加两个轻量机制。

A. Expected Revision

假设 Agent 检索到：
topic: tech-stack
revision: abc123


之后 Agent 根据这个版本生成新内容。

写入时：
save_memory(
  topic = "tech-stack",
  expected_revision = "abc123",
  content = "..."
)


如果此时另一个 Agent 已经修改了该文件：
当前 revision: def456
预期 revision: abc123


omem 应拒绝本次覆盖，并返回版本冲突。

这样就避免了典型的 Lost Update 问题。

这里的 revision 可以使用当前 Markdown 正文的 SHA-256 哈希，不需要额外的数据库。

B. 写入前差异检查

对于已有 Topic，omem 可以在返回结果中提供：
operation: replace
topic: tech-stack

previous:
用户主要使用 PHP。

incoming:
用户主要使用 Rust。

warning:
Existing content will be replaced.


Agent 在看到这个结果后，才能更好地理解自己正在执行什么操作。

不必强制所有更新都经过用户确认，但至少要让写入行为可见。
第三层：历史和证据管理
这部分由 omem 实现。

每次更新：
- 保存 Git 历史。
- 生成写前快照。
- 重新锚定当前内容的证据。
- 不继承与当前内容无关的人工审阅记录。
- 更新成功后重新生成索引。
这里尤其需要解决前面提到的证据污染。

我建议把 evidence 的含义限定为：

支持当前版本内容的证据，而不是这个 Topic 历史上出现过的所有证据。

历史证据由 Git 历史和原始 sessions 保存。

这样就不必引入一套 Claim 级数据库。
关于置信度，我还有一个更重要的设计建议
你目前将 confidence 作为一个数字：
- 0.35：未锚定。
- 0.55：已锚定。
- 最高自动加成至 0.80。
- 0.90：人工过目。
这很适合用于排序，但我认为需要重新定义它的含义。

因为：

人工阅读过，不代表人工确认事实正确。

例如，我阅读了一条：
用户准备辞职。


但我只是看到了这句话，并不代表我确认了这件事，更不代表它现在仍然有效。

所以：
- Evidence：有没有原始依据？
- Confidence：当前内容的证据支持程度。
- Review：人是否看过当前版本？
- Freshness：内容是否可能已经过期？
这几个概念不应该全部由一个数字承担。

尤其是你当前的更新继承逻辑，会保留 confirmations 和 last_confirmed。如果正文改变，旧的人工过目记录就可能被误认为适用于新正文。

我建议：
1. confidence 继续作为排序分数，但不要对外宣传为事实正确概率。
2. 人工过目记录必须绑定到具体版本。
3. 正文发生变化时，当前版本的审阅状态失效。
4. 不增加复杂的 verified 状态机。
可以使用 reviewed_revision，记录人工看过的是哪个内容版本。

这比恢复一个简单的 verified=true 更严谨。
本环节最终决策
必须由 omem 实现
- 安全写入。
- 写前快照。
- Revision 检查。
- 并发写入保护。
- 当前版本证据管理。
- 写入结果和差异提示。
- 版本级审阅状态。
交给 Agent
- 判断新旧内容是否相同。
- 判断应该覆盖还是追加。
- 判断是否存在事实冲突。
- 判断是否需要询问用户。
不做

5. Memory Forgetting：记忆遗忘
omem 实现生命周期管理
Agent 辅助识别过期

我认为这个环节恰恰不需要做得特别智能。

原因很简单：

一个人的历史不应该因为 AI 觉得它不重要就消失。

例如：
- 以前使用 PHP，现在使用 Rust。
- 以前想离职，现在决定留下。
- 以前对某个技术有偏见，现在改变了看法。
这些旧信息可能已经不再适用于当前回答，但仍然有历史价值。

因此，我建议把「遗忘」拆成三个概念。
A. 不再参与检索
例如：
active → stale


旧信息保留，但默认降低检索权重。

当前实现已经支持这个机制，我建议保留。
B. 归档
例如：
active → archived


将不再需要的记忆移入 archive。

它仍然可以被用户查阅，但不再作为默认记忆参与回答。
C. 真正删除
例如：
omem redact --topic xxx


只有用户明确要求，或者用户通过明确的管理操作授权，才执行硬删除。

这点应该成为 omem 的长期设计原则。
我建议不要实现自动遗忘算法
很多记忆框架会使用：
- 时间衰减。
- 访问次数。
- 重要性评分。
- 遗忘阈值。
- 自动压缩。
- 自动合并。
这些机制在 Agent 工作记忆中可能很有价值。

但对于个人长期记忆，它们存在一个问题：

被频繁访问的信息，不一定比很少访问的信息更重要。

例如，用户可能每个月都会询问一次数据库配置，但十年前的一段人生经历可能只会在某个特殊时刻被提起一次。

如果按照访问频率决定记忆是否保留，结果可能恰好相反。
一个我认为值得做的小功能
可以让 Agent 发现过期记忆，并提出审阅建议。

例如：
Topic: current-work

Current memory:
用户目前在某公司担任 PHP 开发工程师。

Evidence:
2025-03

Potentially stale:
最近的会话中提到正在考虑转型。

Suggested action:
Review this memory.


注意，这里只是建议。

Agent 不直接修改，不自动归档，更不能直接删除。

用户可以通过 omem review 决定如何处理。
本环节最终决策
必须由 omem 实现
- active / stale / archived 状态。
- 可逆归档。
- 硬删除。
- Git 历史清理策略与用户告知。
- 过期状态管理。
交给 Agent
- 识别潜在过期信息。
- 提出审阅建议。
- 发现新旧信息的变化。
不做
- 自动硬删除。
- 仅根据访问次数遗忘。
- 强制时间衰减算法。
- AI 自主决定哪些人生经历不值得保留。


三、五个环节之外，还有三个横向问题
这三个问题容易被遗漏，但实际上决定了 omem 能不能长期可靠运行。
1. 记忆的可信度与来源追溯
我建议 omem 将来形成这样一条证据链：
Session

用户原始表达


Evidence

来源会话、原文引用、时间


Memory Revision

某一版本的记忆内容


Current Memory

当前有效版本

Git 负责保存版本变化；omem 负责当前版本与证据的对应关系。

不需要把这套关系做成数据库中的图结构。

只要 Markdown 中的证据能被验证、版本变化能被追溯，就已经很有价值。
2. 隐私和安全
这是本地记忆产品不能忽略的事情。

你的会话原文中可能存在：
- API Key。
- 个人信息。
- 工作项目的商业秘密。
- 客户资料。
- 家庭和私人生活信息。
当前 omem 已经具备通用敏感凭证脱敏、路径排除和 work profile 等机制，但身份证、手机号、薪资等内容不会自动过滤。

我建议未来增加的不是复杂的 AI 内容审查，而是：
能力	优先级
会话目录排除	P0
凭证脱敏	P0
本地数据访问权限说明	P0
远程备份风险提示	P0
指定 Topic 不参与备份	P2
敏感记忆加密	P2
复杂权限系统	暂不做

尤其要注意：Git 删除不等于远端历史中的数据已经消失。redact 应明确说明本地历史和远端备份的处理范围。
3. 可测试性
我建议把 Memory Evaluation 从一个独立的智能评分系统，变成一套普通的自动化测试。

不需要调用大模型，也不需要收费 API。

只测试确定性行为：
- 同一条记忆重复写入是否去重？
- 证据是否真的存在？
- 同一个 Topic 更新后，旧证据是否错误继承？
- stale 是否降低检索优先级？
- archived 是否从默认搜索消失？
- 两个进程同时写入是否丢失更新？
- 外部用 Obsidian 修改 Markdown 后，索引是否正确更新？
- redact 是否真正删除指定范围内的数据？
模型质量评估可以作为独立的可选实验，不应该成为核心产品的依赖。

四、最终职责划分

Agent 理解世界，omem 保证理解结果能够被安全保存、查找、追溯、修正和删除。

这应该成为今后所有功能评审的第一条判断标准。
