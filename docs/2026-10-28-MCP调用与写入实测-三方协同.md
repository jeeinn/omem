### A. 读：真实客户端链路（`mcp__omem__search_memory`）

**A1 / A2 — topic 精确检索与中文多词检索（R1/R2）**

调用 1：`{"topic":"car-purchase-requirements","detail":true}`

```

  家用车选购需求与决策记录（workbuddy 微信端，2026-04-08 起）

- 有 `status=active`、`verified`、`confidence`、`source`、绝对路径 —— MCP 侧信息面是够的（C3 的问题只在 CLI 侧，见 A6，且已被证伪）。
- 默认不混入 superseded：同一 topic 下真实仓有 3 份 superseded，本条只返回 1 条。
- 返回**没有**字符范围、没有可复制的「纯净片段」；要引用只能整段读 body。

调用 2：`{"query":"家用车 选购 预算"}` → `matched 1 · showing 1`（预览 1 行，末尾 `Full text: pass detail=true.`）。中文 4 词 AND 没有误召回。

**A3 — `scope=sessions` 的摘录质量（R3 / 补测 C2）**

调用：`{"query":"瑞虎","scope":"sessions","top_k":2}`

```
- workbuddy:66a01cd3-… · local:7578434e · absorbed
  『…力**：2.0TGDI发动机+爱信8AT，最大扭矩400N·m ***2. 奇瑞瑞虎7L / 全新瑞虎7 / 瑞虎5运动版** — 4月8日上市 - **瑞虎7L*…』
```

核对原文：该命中在会话文件第 42 行，属于 `## assistant` 段（会话内 `## user` 在第 11 行、`## assistant` 在第 22/25/28 行）。**摘录给出的是一段 assistant 生成的车型表**，而 `save_memory` 的 evidence 只认 `## user` 段 —— 即：摘录越"好读"，越可能是不能当证据的那一段。

再用标识符命中：`{"query":"openclaw-weixin","scope":"sessions"}`

```
- workbuddy:66a01cd3-… · absorbed
  『…"openclaw-weix…』
```

摘录只剩 14 个字符，且命中的是元数据围栏里的 `message_id`。原因（源码）：FTS 路径 `snippet(sessions_fts, 1, '', '', '…', 12)` 以 **token 为半径 12**，LIKE 兜底 `manualSnippet` 以 **code point 为半径 40** —— 两套口径（`src/core/search.ts:188` 与同文件注释 212–213），标识符类命中会退化成噪音。

**A4 — 零结果与错误文案（R4）**

```
{"query":"zzzqxnonexistenttopic"}
→ No memories found matching "zzzqxnonexistenttopic".
  Tip: Chinese keywords need at least 3 characters (FTS5 trigram); shorter terms automatically fall back to substring matching.
  Tip: archived and superseded entries are excluded by default; pass status to include them.

{"query":"大一点的车 六座","scope":"sessions"} → No transcripts found matching "大一点的车 六座".

`Found 0 :` 空占位**不存在**了：`formatNoHits` 在 tag `v0.1.0-beta.8:src/core/search-format.ts` 里就已存在，CLI/MCP 共用同一实现。**此条不是 beta.8 的缺陷，是更早版本的现象。**

一处不对称（新增，P2）：**save 侧有近义 topic 提示，search 侧没有**。`{"topic":"no-such-topic"}` 只回一句 `No document found`，不提示"最接近的是 xxx"；而写侧同一个机制会主动说 `Topic "full-doc2" is close to existing "full-doc"`（见 C6）。

旧 2026-10-28-b008dc: status: superseded  confidence: 0.9  verified: true  source: manual
```

回执里 **没有一个字**提到「前一份是 verified / 0.9 被丢掉了」。缓解事实（beta8 未提）：旧文件仍保留 `verified: true`，也就是"验证状态"没有蒸发，只是**挂在了一个默认检索不到的历史版本上**。所以 B3 的损失是"活文档降级 + 调用方不知情"，不是"验证信息丢失"。MCP 侧仍无回升通道：`confirm_ids` 只到 0.8（W5：`(confidence up to 0.8, still unverified)`）。

**D3 — 2000 字上限的真实行为（W6/W7，本轮最重的发现之一）**

```

→ Saved (id: 2026-10-28-8af40c …). Truncated: 2800 -> 2000 chars. Shorten content or split the topic.
落盘 body = 2001 字符（2000 + "…"），YAML frontmatter 完整，status: active
```

文件仍是合法活文档（`truncate()` = `slice(0, n-1) + '…'`，`src/core/util.ts:46`），**截断有回执**，这条不算隐雷。真正的雷是"并进满文档"：

```
base 1,990 字符的活文档 → 追加第 99 条新事实（73 字符）→ merged 2,063
→ Saved (…). Superseded: 2026-10-28-4f2525.
  Truncated: 2063 -> 2000 chars. Shorten content or split the topic.

回读落盘 body：
  …\n49. 既存结论第 49 条：用来占满 2000 字预算的既有事实，内容无意义。\n99. 新增事实：…
  contains 新增事实: True
  contains 指数退避: False      ← 关键内容被吃掉
```

**新事实被切成「99. 新增事实：…」——语义上是半句，形式上是一条完整的编号结论。** 这比"写不进去"更危险：调用方看到 `Saved` + `Truncated` 会以为"记下了但太长"，实际落盘的是一个不可用的半截事实，而它是新的 active 文档。真实仓已有同型样本（W16）：`2026-10-27-1f19b7.md`、`2026-10-27-574cdd.md` body 恰好 2,001 字符，结尾分别是 `…\n1…` 与 `…\n9. 坑：write 覆盖同名 internal/agents/harn…`。

用**围栏里的 JSON** 当 evidence：

```

- `message_id` / `timestamp`（不是用户说的话）→ **算 grounding 成功，0.55**
- assistant 段（用户没说过）→ 0.35

即 `Grounded 1/1` 目前只证明"字符串在 user 段里出现过"，**不证明它是用户表达的事实**。任何 Agent（或任何把 MCP 当写入口的上游）都可以用元数据刷到 0.55。这条 beta8 报告没有；它把 C2 描述为"复制引文会带进元数据导致 grounding 失败"，实测方向相反：**元数据不但不会导致失败，还能顶替证据。**

## 5. 写入环节可改进点

### 契约

1. **2000 字 + 整篇重发 = 满文档吸收必然损坏**（D3）。真实仓 4/58 份 active ≥1800 字（6.9%），superseded 里已有 2 份被截到 2,001。契约缺的是"追加"语义（append / 分节），而不是把上限调大——调大只会让下一次重发更容易被截。
2. **截断落在尾部，而新事实总在尾部**：D3 实测新事实只剩 `99. 新增事实：…`。截断策略与"更新活文档"的语义方向相反。
3. **verified 只能由 `omem add` / `review --confirm` 产生（W5）**，而这两条都只在 CLI。MCP-only 调用方永远无法把文档从"候选"提升到"已验证"，只能`confirm_ids`到 0.8。

### 回执

4. **supersede 掉 verified 文档时回执不提代价**（D2）。调用方看到 `Saved … Unverified entry` 无法区分"新写的"与"把 0.9 换成 0.55 的"。一句 `previous verified status (0.9) was dropped; old version kept at <id>` 就够。
5. **截断回执没说"丢了什么"**：`Truncated: 2063 -> 2000 chars` 精确到数字，但没说"被丢弃的是你刚追加的第 99 条"。调用方无法判断损失是否可接受。
6. **落盘不进 git 的回执缺失**（W14）：13 次写入 0 提交，`save_memory` 返回体末尾没有 beta8 建议的那句"本轮 N 个文档未入版本历史"。

### 不变量

7. **grounding 不变量被元数据击穿**（E2）：`## user` 段里的 `Conversation info (untrusted metadata)` 与 JSON 可以充当证据，`0.55` 与 `Grounded 1/1` 因此不再意味着"用户说过"。这条直接决定 `verified:false` 候选值不值得信。
8. **`copies: N` 的吸收语义**已写进头部文案（"distilling the listed one covers all copies"），但写入侧没有对应参数（无法显式声明"这一条覆盖 N 份"），语义只存在于文案里。

- `assistant` 段：**25/26 组各不相同**；最大组 25 份 copies 携带 **25 个不同回答**（1,075–3,073 字符）。唯一"真一样"的组是 assistant 段全空的那组（1 组）。
- 因此 `guide.ts:126` 的 "distilling the listed one covers all copies" 是**错误承诺**：copies 只共享用户提问，各自的结论完全不同。按这句话只吸收 1 份，最多静默丢掉 24 份独立回答里的结论。
- **对账影响：D1 从「已修（文案层）」退回「误修」**——文案没有解决歧义，而是给了一个会造成静默丢失的确定性错误。这条同时是**契约漂移**的直接样本（见 §8.4）。

## 7. 给架构师的 5 条硬问题（只给证据，不给方案）

1. **grounding 的证明力边界在哪里？** 实测 `Grounded 1/1` 可以由 `## user` 段里的 `message_id`/`timestamp` JSON 满足（0.55），也可以由 assistant 段全文满足失败（0.35）。那么 `confidence=0.55` 这个数字，当前到底在度量"用户说过"还是"字符串出现过"？如果两者不等价，所有依赖它排序/过滤的读路径都建在沙上。

2. **2000 字上限与"一主题一份活文档"不变量能否同时成立？** 实测：1,990 字文档并入 73 字新事实 → 落盘 `99. 新增事实：…`，关键内容消失而文档仍标 `active`；真实仓 active 里 4/58 已 ≥1800 字，2 份历史版本恰好停在 2,001 字符。若不变量要求"整篇重发 + 2000 上限"，那么一个主题的终身信息量上限就是 2000 字——这是设计意图，还是两处约束相撞后的副作用？

3. **写入路径的"已验证"状态可否与版本解耦？** 实测 supersede 后：新 active `verified:false / 0.55`，旧版本 `status:superseded / verified:true / 0.9`，回执不提这件事，MCP 无回升通道（`confirm_ids` 封顶 0.8）。也就是说 verified 永远绑定在**某个不再被检索的版本**上。这套模型在"文档级验证 + 内容级追加"并存时，谁代表用户确认过的事实？

4. **MCP 工具面的最小性是否以"运维不可执行"为代价？** 实测默认 2 工具 / 10,219 字符，`OMEM_MCP_TOOLS=feedback` 只多一个 354 字符的 feedback；`topic_list` / `redact_memory` 一律 `Unknown tool`。而 PROCESS.md 自己规定 `omem skip`、`omem add`、`review --confirm`、`topic list` 是流程必需。若"只用 MCP"是产品纪律，那当前纪律在自身文档里就是不可执行的——这条边界该由谁定义？

5. **清单的可读性瓶颈是"内容多"还是"渲染方式错"？** 实测 PROCESS.md 80,310 B：session 行 94.1%，其中 50.7% 是与 36 位 uuid 完全冗余的绝对路径；`## Existing topics` 只占 1.6% 却只列 5/58 条；`omem context --for plain` 生成 16,920 B 的索引视图（58 active）。同一批事实有三种体积（80KB / 16.9KB / 20,060 token 估算），哪种是"Agent 开工视图"的正确答案？

### 8.5 快照口径修正（`immutable=1` 漏读 WAL，架构师评审提出）

初版 §1 用 `mode=ro&immutable=1` 取基线。`immutable=1` 会让 SQLite **不读 WAL**（真实仓 `omem.db-wal` = 40,446,072 B），因此拿到的是主 db 的旧快照。按 `AGENTS.md`「Markdown 是事实源」，本节一律以**磁盘解析**（`knowledge/` + `archive/` 共 109 份）与 **`mode=ro`（含 WAL）** 双口径交叉核对。

| 指标 | 旧值（`immutable=1`） | 新值（`mode=ro`，含 WAL） | 磁盘事实源（109 份解析） | 差异原因 |
| --- | --- | --- | --- | --- |
| sessions | 1,101 | 1,101 | 1,101 份会话文件 | 无差异（sessions 表早已 checkpoint） |
| entries 总数 | 107 | **109** | 109 | WAL 未回放，少 2 行 |
| active | 57 | **58** | **58** ✓ | 差 1：最新一次 `car-purchase-requirements` 合并（22:59–23:02）只落在 WAL |
| superseded | 41 | **42** | **42** ✓ | 同上，被 supersede 的旧版 |
| archived / stale | 7 / 2 | 7 / 2 | 7 / 2 ✓ | 无差异 |
| verified=true（全部条目） | 61 | 61 | 61 ✓ | 无差异 |
| verified=true 且 active | — | — | **40** | 新增口径，供 H7 使用 |
| `PRAGMA journal_mode` | `delete`（伪值） | `wal` | — | `immutable=1` 连日志模式都读成旧值，方法问题的旁证 |

**结论 1（影响 §1）**：环境行的 active 应为 **58**，与磁盘渲染一致；57 是 WAL 未合并的旧值。`mode=ro` 与磁盘解析两个口径**逐项一致**（58/42/7/2 = 109），说明索引本身没有漂移，问题只在我的取数方式。

**结论 2（重核两个验收基线，均无差异）**：

| 基线 | 原报 | 重核 | 差异 |
| --- | --- | --- | --- |
| ① active 中 body ≥1800 字 | 4 / 58 | **4 / 58**（1935 / 1930 / 1927 / 1841） | **无差异** |
| ② body 恰好 2,001 字符且以 `…` 结尾 | 2 份 | **2 份**（`2026-10-27-1f19b7`、`2026-10-27-574cdd`，均 superseded） | **无差异** |
| 附：active 中 >2000 字 | 0 | **0** | 无差异 |

这两项本来就取自磁盘文件的正文长度，不经过索引，所以不受 WAL 影响——但初版只扫了 `knowledge/`（102 份），漏掉 `archive/`（7 份）；补全后 active 仍 58、截断样本仍 2，结论不变。

**结论 3（H5 样本未受 WAL 影响，三个数全部成立）**：

| H5 口径 | 原报 | 重核 |
| --- | --- | --- |
| 会话文件 / user_hash 组 | 1,101 / 958 | **1,101 / 958** |
| `copies≥3` 的组 | 26 | **26** |
| assistant 段有实质差异的组 | 25 / 26 | **25 / 26** |
| user 段逐字一致的组 | 26 / 26 | **26 / 26** |

H5 直接读会话文件正文，不依赖索引，因此 WAL 不影响其判定；「吸收一份 = 吸收全部 N 份」仍为**错误承诺**，D1 仍应从「已修」退回「误修」。

**结论 4（对 §2 汇总表的影响）**：**无任何条目结论翻转**。汇总表里与计数相关的行分别是 W16「active 58 份中 ≥1800 字 4 份」、W6/W7 的 2,001 字符截断样本、R6 的 PROCESS.md 80,310 B——前两组已按磁盘口径重核且数值不变，R6 是文件字节数、与索引无关。唯一需要改写的是 §1 环境行的 active 计数（57 → 58），已在上表与 §1 同步。

**方法论留存（写给下一个做实测的人）**：`immutable=1` 只适合"确定没有 WAL 或在拷副本"的场景；对活库取基线必须用 `mode=ro`，并同时用磁盘事实源交叉验证。两者不一致时，先怀疑取数方式，再怀疑索引漂移。
