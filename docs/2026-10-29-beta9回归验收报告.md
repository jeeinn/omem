## 1. 结论

**不可发布**（2 条 P0 阻塞 + 6 条 P1）。

三个理由：

1. **T04 在真实数据上没有做到「无损」，而且已经踩在预算悬崖上。** 同一批 1,101 份会话、同一渲染器：`beta.8` 渲染 110,615 B / 611 行 / 546 会话行 / 0 隐藏；`beta.9` 渲染 **29,970 B**（预算 30,000，余量 **30 B**）/ 626 行 / **518 会话行** / **30 份会话被隐藏**（`…30 more in this group — hidden by the size budget`）。工程师自述「0 隐藏」不成立。同时 `Unassigned sessions` 只列 5 条、实际 235 条，**没有任何 more 标记**。

3. **beta.10 的 token 预算被 beta.9 提前吃掉。** `tools/list` 同口径实测 **9,569 → 11,893 字符（+2,324，+24.3%）**，而 S3 门槛 12,500 相对 QA 基线 10,219 只余 2,281。折回 QA 口径约 **12,543**，**已越过 12,500**；规划里「+700 topic_list / +900 pending_memory」的四工具面算式（12,154）不再成立。

三项都不是「写进 release note 就行」的性质：前两项是「文案说不会发生、实际会发生」，第三项会让 beta.10 一开始就带着超预算的债。

## 6. 两个「偏离」的判定

### 偏离 1：预算降级阶梯与规划 §9.2 相反（先丢 `confidence · created`，保留 id）

**实测对比（真实 1,101 会话，两组都在 level 2 收敛）：**

| 阶梯 | 字节 | 会话行 | 隐藏 |
| --- | --- | --- | --- |
| 工程师：level1 丢 `confidence · created` | 29,970 | 518 | **30** |
| 规划 §9.2：level1 丢 topic 的 id 列 | 29,998 | 520 | **28** |

**判定：可以接受，但理由必须改口径。**

- **它并不减少隐藏量**：反而多藏 2 份（id 列比 `0.55 · 2026-10-28` 宽约 1 B/行，58 行 ≈ 58 B ≈ 1.4 行会话）。差异在噪声级（0.7%），所以谈不上「更差」，但绝不能说「因此减少了隐藏」。
- **真实收益在往返数**：保留 id = `supersedes` 一次拿得到，省一次 `search_memory(topic=)`。这是与 T04「降低开工税」一致的取舍，值这 2 份会话。
- **新引入的问题（可接受但需记录）**：level ≥ 1 之后 topic 行没有 confidence，Agent 无法从清单区分 0.9 verified 与 0.55 candidate；**level 3 时连 id 也丢**（只剩名字），那时反而必须二次调用——即该阶梯的最后一档自相矛盾。真实数据未触达 level 3，2,000 会话时仍停在 level 2，风险仅理论存在。
- 建议（最小方向）：release note 与代码注释把理由写成「省一次往返」，不要写「减少隐藏」；给 level 3 的 `names` 行补一句「id 用 `search_memory(topic=)` 取」，现在那句话只在 `names` 模式末尾加了一行，位置在全表之后，指向性弱。
