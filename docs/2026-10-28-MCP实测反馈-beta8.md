# omem MCP 实测反馈（beta.8 现场记录）

> 本文是「边用边记」的实测反馈，不是源码级审计。源码级判断见 `omem-MCP改进建议核查与行动计划.md`（WP1–WP8）。
> 记录环境：omem 0.1.0-beta.8，Windows 11，WorkBuddy MCP 客户端（stdio），真实仓 `~/.omem`（56 活文档 / 1101 会话文件 / index 109MB）。
> 记录时间：2026-10-28 22:50–23:15。

## 摘要

| 指标 | 实测值 |
| --- | --- |
| 本轮成功吸收会话 | 3 个（新建 2 个 topic，合并 1 个 topic 的 4 个历史版本） |
| 单次 `save_memory` 往返耗时 | 2–4 秒，无失败（4 次调用，4 次成功） |
| 单会话吸收的 Agent 侧前置成本 | 读 PROCESS.md（20k+ tokens，Read 工具直接拒绝）+ 解析 session 文件 + 逐字抠 evidence |
| 未吸收积压 | 405 会话（PROCESS.md 口径），按本轮速率约 100+ 轮才能清空 |
| 结论 | **写入通道本身是健康的；瓶颈在「读到该写什么」和「长文档写不进去」两端** |

## A. 已确认修好的（beta.8 正向验证）

1. **`save_memory` 后会刷新 PROCESS.md**。三次写入后 PROCESS.md mtime 同步更新，且被吸收的 session id 立即从待办列表消失（`grep -c <id> PROCESS.md` = 0）。beta.3 时代"A 的缺口"已消除，PROCESS.md 可以作为真实进度标尺。
2. **grounding 反馈可用**。返回体 `Grounded 1/1 quote(s) on the ## user section of <id>` 能直接判断引文是否落地，不需要回头查数据库。
3. **`supersedes` 多 id 生效**。一次传 3 个历史版本 id 全部转 superseded，返回体逐条列出。

## B. 阻断级（P0）

### B1. PROCESS.md 无法被 Agent 直接读取

- **现象**：80,310 字节 / 611 行，`Read` 报 "exceeds maximum allowed tokens (20000)"，只能用 `head` + 正则硬抠。
- **代价**：每次开工前都要花一次工具往返 + 数千 token 才能知道"有哪些活可干"，而列表本身 90% 是路径噪声。
- **建议**：
  1. 每行只给 `collector` + `id` + `(copies: N)` + **一句内容摘要**（首条 user 文本裁 60 字）。清单里 `C:\Users\wei\.omem\sessions\workbuddy\<uuid>.md` 与 id 完全冗余，砍掉可省约 30–40% 体积。
  2. 提供分页视图（`omem context --for <agent> --limit 20 --offset 0`），默认只渲染一批。
  3. 增加「按主题聚类」而非「按 project 聚类」的待办视图：本轮 3 个会话分属 3 个主题，但列表只按 project 分组，聚类信息要 Agent 自己算。

### B2. 2000 字上限 + 整篇重发 = 成熟主题写不进去

- **现象**：`config.process.max_content_chars = 2000`。实测 `matea-phase2-planning` 的活跃版正文 1930 字（97% 满），历史两版正文被截到 2001 字节；`matea-pluggable-brain-decisions` 1841 字。
- **后果**：本轮想把「Hermes Runs API 适配器」并进 `matea-pluggable-brain-decisions`（该主题的正统归属），但加上第 9 条必然超限触发截断，**只能另开 `matea-hermes-runs-integration`**，并在正文里注明"因父文档已满而拆分"。主题碎片化是工具约束逼出来的，不是设计选择。
- **建议**：`save_memory` 支持 `mode: "append" | "replace"`（append 只追加到末尾并做上限检查），或允许"分节"——一节一次写入，`topic` + `section` 双键。这比单纯调大上限更有效：调大只会让单次重发更贵、更容易截断。

### B3. 更新活文档必然降置信，且 MCP 无回升通道

- **现象**：`e2e-gitea-pitfalls` 是 `verified: true` / confidence 0.9。若用它吸收新会话，按不变量必须整篇重发，结果是 `verified → false`、`0.9 → 0.55`（本轮两次写入实测均为 0.55）。
- **实测决策**：**我因此主动放弃了这次吸收**——用一条已验证的高价值排障记录，换取一条未验证的新事实，净损失。这在真实使用中会表现为"越用越不敢用"。
- **建议**：
  1. MCP 补 `verified` 提升通道（等价的 `omem add` / `review --confirm`），哪怕是"两步确认"（先写、用户确认后置 verified）。
  2. 或让 supersede 保留 `verified` 并追加一条 `reverified_by: <session>`，把"文档级验证"与"内容级新增"解耦。
  3. 至少在返回体里显式提示 `previous verified status was dropped`，让调用方知道代价。

## C. 高频摩擦（P1）

### C1. `supersedes` 需要精确 id，等于每次写入先多一次检索

- 每次更新都要 `search_memory(topic=…)` 拿 active id，再写。本轮 3 次写入配了 3 次检索。
- `findActiveByTopic`（服务端已有）完全有能力在 `supersedes` 缺省且 `topic` 命中时自动接管。建议：**`topic` 给定且省略 `supersedes` 时，默认 supersede 该主题的 active 文档**，只在实际无 active 时新建。当前"拒绝 + 让你去查"的行为让 90% 的正常更新变成两次调用。

### C2. evidence 需要逐字复制，但 user 段混着元数据

- 实测 workbuddy 会话的 `## user` 段常带 `Conversation info (untrusted metadata):`、`Sender (untrusted metadata):` 前缀，甚至整段粘贴的 `<conversation_history_summary>`。直接复制会把元数据带进引文，导致 grounding 失败或引用失真。
- 本轮的处理方式是写脚本切分 `## user` 块并剥前缀——这个清洗逻辑本该在 omem 侧（`scope=sessions` 已经做了类似截取），而不是每个 Agent 各写一遍。
- **建议**：`search_memory(scope="sessions")` 的返回体直接给"可复制的纯净引文片段"（去掉 metadata fence），并标注它的字符范围。

### C3. CLI 的 `search --all` 不显示 status，Agent 会误判重复

- **现象**：本轮一开始据 `search 家庭 --all` 与目录文件列表，误判"`car-purchase-requirements` 有 4 份活跃文档，违反不变量"。实际只有 1 份 active，另外 3 份是 superseded 历史版本——**CLI 输出里没有任何 status 标注**。
- 后果：误判会导致无谓的"合并"动作（我确实多传了 3 个已 superseded 的 id）。
- **建议**：CLI 输出行加 `[active]` / `[superseded]` / `[archived]` 徽标（MCP 的 `detail` 输出已经有 `status=active`，CLI 对齐即可）。

### C4. 运维动作完全没有 MCP 通道，纪律无法维持

- 本轮必须做的三件运维事——`redact --id`（删测试条目）、`topic list`、`backup`——**MCP 面只有 `search_memory` / `save_memory`**，只能回 CLI 直连 `~/.omem`。
- 这与"优先用 MCP、不要直接改目录"的使用纪律直接冲突：用户要求"清理完就只用 MCP"，而清理本身恰恰没有 MCP 路径。
- **建议**：把 `redact`（需二次确认参数）、`skip`、`topic list` 纳入可选工具集（沿用 `OMEM_MCP_TOOLS` 开关），至少让 `topic list` 可读——否则 Agent 永远不知道该用哪个 topic 名。

### C5. 写入不落 git，工作区长期脏

- 本轮结束时 `git status` 有 43 个未提交改动，其中包含多份 `knowledge/*.md`。`save_memory` 明确不 commit，需要用户手动 `omem backup`。
- **建议**：`save_memory` 返回体末尾提示"本轮 N 个文档未入版本历史，`omem backup` 可固化"；或在 `save_memory` 首次落盘后自动做一次本地 commit（远端推送仍需显式）。

## D. 可优化（P2）

1. **`copies: N` 语义没写清**。PROCESS.md 说"Sessions sharing one user-section fingerprint are collapsed"，但没说"吸收一份是否等于吸收全部 N 份"。本轮只能按"是"处理并在此记录假设。
2. **分组口径不自洽，且计数不同步**。头部同时写 "This batch: 5 group(s) / 638 session(s) shown" 与 "64 group(s) and 405 session(s) still unabsorbed"——638 > 405，两个数字不是同一量纲（一个含 copies、一个不含），没有说明。实测吸收 2 个会话后：`shown` 从 638 降到 636，而 `still unabsorbed` **仍是 405 未变**，说明后者不是实时重算而是缓存值。Agent 若以此判断进度会得出"白白干了"的错误结论。
3. **`omem topic list` 的 TITLE 列会截断**，长标题（如 `father-lm-pci-recovery` 那条）在表里被切掉一半，导致"这个 topic 到底记了什么"仍需点进去看。
4. **无进度度量**。没有"已吸收 / 未吸收 / 跳过"的比率视图，用户无法判断"记忆吸收到什么程度了"。建议 `omem status` 输出一行：`405 unabsorbed / 1101 collected / 56 topics`。
