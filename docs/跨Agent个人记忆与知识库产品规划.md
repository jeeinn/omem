## 1. 产品概述

### 1.1 一句话定位

一款**本地优先**的跨 Agent 个人记忆与知识库产品：自动采集各 AI 工具的会话数据，通过 LLM 加工为结构化的 Markdown 知识库，以标准协议（MCP）接入任意 AI Agent，实现记忆的**跨会话、跨 Agent、跨设备**复用，并逐步沉淀为个人知识库与技能库。

### 1.2 核心链路

```
本地软件（自动采集会话文件）──┐
                              ├──► 总结记忆（LLM 加工）──► 统一备份 / 跨会话使用 ──► 个人知识库 / 技能库
本地 MCP（Agent 主动调用）───┘
```

### 1.3 解决的问题

当前 AI 工具的记忆能力呈现严重的**碎片化与封闭化**：

| 现状 | 问题 |
|---|---|
| ChatGPT / Claude 等云端记忆 | 封闭在各自生态，不可导出、不可跨工具使用 |
| Claude Code 的 CLAUDE.md / Cursor Rules | 仅限单一工具，需手工维护 |
| 每个会话结束即遗忘 | 用户在工具 A 里教会的偏好，工具 B 一无所知 |
| 个人经验散落在无数会话中 | 无法沉淀、检索、复用 |

**没有一个主流产品把"通用接入 + 自动采集 + 高质量加工 + 跨设备同步"全链路打通**——这是本产品的机会。

## 2. 市场与社区现状

### 2.1 相关开源方案盘点

| 项目 | 路线 | 与本产品的关系 |
|---|---|---|
| **mem0 / OpenMemory** | 记忆层框架：LLM 抽取事实→去重合并；OpenMemory 提供本地 MCP 记忆服务 | 最接近的竞品/可复用组件；但采集端弱，依赖 Agent 主动调用 |
| **Letta（原 MemGPT）** | Agent 自编辑分层记忆 | 更偏 Agent 框架，不易作为独立记忆库嵌入 |

| **claude-mem** | CLI hook 自动总结 Claude Code 会话存入 SQLite | "本地软件主动收集会话文件"的现成参考，但只支持单一工具 |
| **Basic Memory** | 对话沉淀为本地 Markdown 知识图谱 + MCP 暴露 | "Markdown 即知识库"设计的最佳参考 |
| **agentmemory (rohitg00)** | MCP server + REST，SQLite + iii 引擎，12 个自动钩子采集，20 个 Agent 适配器，BM25/向量/图混合检索 | **最直接的竞品**：已实现"自动采集 + MCP 接入 + 跨 Agent 共享"全链路，但仅限编程 Agent 场景，详见 2.2 |
| **LangMem / cognee / Hindsight** | 各类记忆框架/知识图谱管道 | 生态位重叠，非直接竞品 |

### 2.2 重点竞品：agentmemory 深度对照

[agentmemory](https://github.com/rohitg00/agentmemory)（GitHub Trendshift 热门项目）与本项目构想高度重叠，相当于本项目规划中 Phase 0–2 的一个已完成实现。逐项对照如下：

| 维度 | 本项目构想 | agentmemory 现状 |
|---|---|---|
| MCP 接入 | ✅ 核心设计 | ✅ MCP server + REST API（54 个 MCP 工具） |
| 自动采集会话 | ✅ 双通道采集（watcher 兜底） | ✅ 12 个自动钩子，Claude Code 零手工捕获 |
| 跨 Agent 共享 | ✅ 核心诉求 | ✅ 20 个适配器（Claude Code、Cursor、Codex CLI、Copilot、Gemini CLI、Cline、Aider 等） |
| 混合检索 | ✅ FTS5 + 向量 | ✅ BM25 + 向量 + 图（RRF 融合），本地嵌入可离线 |
| 记忆生命周期 | ✅ supersedes 冲突消解 | ✅ 4 层整合 + 衰减 + 自动遗忘（更完整） |
| 本地优先 | ✅ 核心原则 | ✅ SQLite 零外部依赖，自托管 |
| **用户领域** | **全领域**（生活 + 编程 + 决策…） | ❌ **仅 AI 编程 Agent 场景** |
| **Markdown 事实源** | ✅ MD 为 source of truth，可 Obsidian 互通、可 git | ❌ SQLite + iii 引擎，数据不可直接阅读编辑 |
| **跨设备同步** | ✅ git / Syncthing | ❌ README 未提及 |
| **技能库沉淀** | ✅ SKILL.md 蒸馏 | ❌ 无对应层 |
| Windows 支持 | ✅ 原生 | ⚠️ 推荐 WSL2 |

**对竞争格局的修正判断**：此前"采集覆盖 + 加工质量无人做"的判断已被推翻——agentmemory 已把"通用编程 Agent 记忆层"做成了红海。本项目的差异化空间被压缩至四个维度：**全领域知识库（而非仅编程）、Markdown 事实源与可迁移性、跨设备同步、技能沉淀**。同时它也提供了新选项：作为采集/记忆引擎复用，在其上构建"Markdown 投影 + 同步 + 技能蒸馏"层（见 7.1 技术路线决策）。

> 注：agentmemory README 自报的检索指标（LongMemEval-S 95.2% R@5 等）与其竞品对比数字均来自各自数据集或厂商自报，非同基准正面对比，参考价值有限，需实测验证。

### 2.3 行业趋势判断

1. **MCP 已成为事实标准**：Claude Code、Cursor、Copilot、OpenCode、Cherry Studio 等主流 Agent 均支持 MCP client。"让不同 Agent 通用接入"这一最大难点已被协议层基本解决。
2. **Markdown 文件记忆被验证**：Anthropic 的 CLAUDE.md/AGENTS.md 模式与 Agent Skills（SKILL.md）证明了"纯文件 + 上下文注入"路线的工程可行性。
3. **"通用编程 Agent 记忆层"已成红海**：agentmemory 等项目已实现"自动采集 + MCP 接入 + 跨 Agent 共享"全链路（详见 2.2），此前判断的空白区正被快速填补。剩余空白在**全领域泛化、数据可迁移性（Markdown）、跨设备与技能沉淀**。
4. **记忆横向评测兴起**（LoCoMo 等基准）：社区对加工质量的关注度上升，加工质量仍将是产品核心竞争力之一。

### 2.4 竞争定位（2026-10 修订）

```
            用户领域覆盖（编程 → 全领域生活/决策）
                  ▲
                  │
     本产品 ★     │
                  │  （空白区：全领域 + 可迁移 + 跨设备 + 技能）
                  │
                  │   agentmemory / mem0 / OpenMemory
                  │   （编程 Agent 记忆层，已红海）
                  │
 ChatGPT Memory ──┤──────  Zep / Letta
（封闭、单一生态） │     （重、偏框架）
                  └──────────────────────► 数据可迁移性（SQLite 封闭 → Markdown 开放）
```

**差异化主张（修订）：编程 Agent 记忆层已无机会（agentmemory 已做透），本产品定位为全领域个人知识库——Markdown 事实源（可迁移、可 git、可 Obsidian）、覆盖生活与决策场景、跨设备同步、沉淀为技能资产。壁垒不在协议与采集（已商品化），而在领域泛化的加工质量与数据主权体验。**

## 3. 用户与场景

### 3.1 目标用户

- ** primary**：同时使用 2+ AI 工具的重度用户（开发者、知识工作者），对隐私敏感，希望本地掌控数据。
- **secondary**：希望沉淀个人知识资产的长期主义者（生活决策、编程经验、项目上下文）。

### 3.2 核心场景

1. **跨工具记忆延续**：在 Claude Code 里教会的项目约定，回到 Cursor / Cherry Studio 继续生效。
2. **自动知识沉淀**：一次高质量的会话（如购车决策、技术方案讨论）结束后无需任何操作，结论自动进入个人知识库。
3. **跨设备办公**：公司电脑与家用电脑共享同一份记忆与知识库。
4. **技能复用**：高频沉淀的经验（调试套路、写作模板、踩坑记录）蒸馏为技能文件，任意 Agent 可加载。
5. **生活+编程统一**：不只是代码记忆，而是覆盖生活决策、消费研究、学习笔记的全领域个人知识库。

## 4. 产品设计原则

1. **本地优先（Local-first）**：所有原始数据与知识库存于本地；LLM 加工可自配（API 或本地 Ollama），隐私敏感内容可全离线。
2. **Markdown 为唯一事实源（Source of Truth）**：向量索引、图谱等一切派生数据皆可丢弃重建；用户可随时手工编辑（Obsidian 直接打开即是知识库）。
3. **双通道采集**：MCP 主动写入（精确）+ 会话文件扫描（兜底），同一会话需去重。
4. **渐进式信任**：从"只读检索"到"自动写入"分级开启，用户始终可审查、编辑、删除任何记忆。
5. **零部署门槛**：单二进制/单命令启动，无独立数据库服务。
6. **开放生态**：MIT 开源；核心（存储引擎 + 加工流水线 + MCP server）与适配器（各 Agent 的采集/接入插件）严格分离——核心由本项目维护，适配器欢迎社区贡献，让国内外各类 Agent 都能被适配和完善。

### 5.1 MCP 工具集设计（v1）

| 工具 | 说明 |
|---|---|
| `search_memory(query, tags?, top_k?)` | 混合检索（FTS5 关键词 + 向量语义） |
| `save_memory(content, source?, tags?)` | Agent 主动写入记忆 |
| `list_memories(tag?, since?)` | 按标签/时间浏览 |
| `delete_memory(id)` | 删除（可审计） |
| `get_skill(name)` | 加载已蒸馏的技能文件（Phase 4） |

### 5.2 记忆条目格式

```markdown
---
id: mem_20261015_a3f2
type: preference | fact | decision | experience | skill
domain: programming | life | project | ...
source: claude-code | cursor | mcp-direct | import
session: <会话指纹，用于去重>
created: 2026-10-15
confidence: 0.9
verification: unverified | verified   # 自动采集默认 unverified，用户/Agent 确认后晋升（参考 memoir）
status: active | superseded
supersedes: mem_xxx
---

用户偏好 TypeScript 而非 Python 处理 MCP 相关代码……
```

`supersedes` 字段实现轻量级冲突消解（新事实推翻旧事实时旧条目标记为 superseded 而非删除），借鉴 Graphiti 的时序思想但不上图数据库。

### 5.3 实现细节与关键取舍

#### 5.3.1 会话产物是否纳入知识库

会话中除了对话文本，还会产生大量"产物"（artifacts）：代码块、生成的文件、命令输出、链接清单等。取舍原则：**结论入库，产物留索引**。

| 产物类型 | 策略 | 理由 |
|---|---|---|
| 结论性知识（决策、偏好、经验教训） | ✅ 提取为记忆条目 | 这是知识库的核心资产 |
| 关键代码片段（如调试出的正则、一次性脚本） | ✅ 精简后入库，标注来源 | 高复用价值，但需 LLM 判断"值得留" |
| 大体积产物（完整文件、报告、图片） | ⚠️ 不入库本体，存"产物仓库"（`artifacts/` 目录）并在记忆条目中留相对路径引用 | 避免 MD 膨胀；artifacts 目录不进 git 或走 LFS，同步策略独立 |
| 过程性内容（中间推理、试错过程） | ❌ 默认丢弃，仅在"踩坑经验"场景提炼教训 | 信噪比太低 |
| 命令输出/报错堆栈 | ⚠️ 仅当形成"问题→解法"对时入库 | 结构化经验价值高 |

配套机制：产物仓库与知识库同源但分离（`knowledge/` 进 git，`artifacts/` 可选同步），记忆条目 frontmatter 增加 `artifacts: [path...]` 字段做引用；检索命中条目后 Agent 可按需读取产物。

#### 5.3.2 跨设备项目身份解析

问题：换电脑后，同一项目的 git 克隆目录不同（公司 `D:\work\foo`，家里 `~/code/foo`），若记忆条目直接存绝对路径，跨设备即失效。解决方案：**项目身份与路径解耦**，采用"项目指纹 + 别名注册表"两层设计：

1. **项目指纹（稳定 ID）**：优先取 `git remote origin` 的 URL 归一化（去协议/用户名/大小写差异）；无 git 时回退到目录内容指纹（关键文件名 hash）。记忆条目只存 `project: foo@github` 形式的指纹，不存本机路径。
2. **本机路径注册表**：每台设备维护一份 `workspaces.json`（指纹 → 本地路径的映射，**不进 git**），采集器据此把会话归因到项目；换电脑只需重新 `register` 一次（可自动扫描常见目录 + 用户确认）。
3. **模糊归因兜底**：无指纹的会话（网页对话、无 git 目录）按对话内容的项目关键词归因，置信度低于路径归因。

这一设计同时解决"同一项目多克隆位置""项目改名/迁移 remote"等场景：指纹变化时提供合并工具，旧记忆条目批量迁移到新指纹。

#### 5.3.3 其他已识别的取舍点（持续补充）

| 细节 | 倾向 | 备注 |
|---|---|---|
| 记忆条目粒度 | 一事一条（3–10 句） | 太粗检索差，太碎检索噪声多，需实测调 |
| 生活 vs 工作/编程是否分库 | 同库不同分区（`domain` 标签）+ 检索时可按域过滤 | 分库会让跨域记忆（如"用编程方法解决生活问题"）丢失 |
| 敏感信息（密钥、隐私） | 加工时黑名单正则 + LLM 双重过滤，条目级 `sensitivity` 标记，跨设备同步可排除高敏条目 | 本地优先原则的延伸 |
| 多轮修正同一事实 | 合并为一条，保留 changelog 在 frontmatter | 避免同一主题碎片化 |
| 记忆条目语言 | 中英混合不翻译，检索用多语 embedding | 忠实原始表达 |

### 5.4 MCP 调用意愿优化（大知识库场景）

风险场景：知识库条目上万后，Agent 面对一堆 MCP 工具可能不愿主动调用（工具描述稀释注意力、检索延迟高、返回太长挤占上下文）。优化组合拳：

1. **工具数量与描述精简**（最关键）：Agent 是否调用取决于工具 description 的"说服力"。v1 只暴露 2–3 个工具（`search_memory` / `save_memory` / `get_skill`），description 写成高召回的触发条件式文案（"当用户提到过往偏好、历史决策、之前的项目经验，或你不确定用户是否告诉过你某事时，先调用本工具检索"），其余能力（list/delete/管理）走 REST API 或 CLI，不给 Agent 看。
2. **返回 token 预算控制**：`search_memory` 默认返回 top-3 条**摘要行**（标题 + 2 句摘要 + id），带 `detail=true` 参数才返回全文——两级懒加载，单次调用占用上下文 < 300 token。
3. **被动注入兜底（不依赖 Agent 主动性）**：自动生成并维护 `MEMORY-INDEX.md`（核心记忆的蒸馏版，< 80 行），通过 CLAUDE.md / AGENTS.md include 或系统提示注入——这是 Claude Code 已验证的模式，Agent 不调工具也能拿到最关键的 20% 记忆，工具检索负责长尾。
4. **检索性能门槛**：MCP 工具响应 > 1s 时 Agent 体验明显劣化（易触发超时/放弃），FTS5 + sqlite-vec 本地查询可控制在 100ms 内；禁止在工具调用路径上做 LLM 二次加工。
5. **调用率可观测**：记录每次 MCP 调用（调用方 Agent、query、命中数），周报分析"应调未调"场景，反哺 description 文案迭代——调用率本身是核心产品指标（见第 9 章）。
6. **上下文分级**：按 Agent 类型提供 `compact` / `full` 两种工具集预设（IDE 内嵌 Agent 上下文紧张，给最简版；CLI Agent 宽裕，给全量版）。

## 6. 技术选型

| 模块 | 选型 | 理由 |
|---|---|---|
| 接入协议 | MCP TypeScript 或 Python SDK | 行业事实标准，生态最广 |
| 知识存储 | Markdown + frontmatter | 人类可读、git 友好、可迁移、Obsidian 互通 |
| 元数据/全文检索 | SQLite + FTS5 | 零部署、单文件、跨平台 |
| 向量检索 | sqlite-vec 或 LanceDB | 嵌入式，无独立服务 |
| Embedding | bge-m3（本地推理）或 API | 中英混合效果好 |
| 加工 LLM | 用户自配（API 或 Ollama） | 隐私分级 |
| 会话采集 | 文件 watcher（chokidar / watchdog） | 各工具会话均落盘为本地文件 |
| 跨设备同步 | git 私有仓库（首选）/ Syncthing | 冲突可 diff、可回滚 |
| 打包分发 | 单二进制（pkg/bun）或 pipx | 零依赖安装 |

**有意不选**：Neo4j/完整图数据库（维护成本过高，Markdown+混合检索覆盖 90% 场景）、独立向量数据库服务（违背本地零部署原则）。

## 7. 路线图（2026-10 修订：基于新竞争格局）

### 7.1 技术路线决策（已锁定）：全自研 + MIT 开源

**决策：全自研存储引擎，不依赖 agentmemory/mem0 等外部引擎；核心代码 MIT 开源。**

理由：

1. **数据格式自主权**：Markdown + 自研引擎是本产品最大差异化（可迁移、可 git、可 Obsidian），引入 SQLite 封闭引擎做投影会侵蚀这一根基，且双写一致性成本高。
2. **适配生态是核心战略而非成本**：国内外 Agent 格局碎片化（Kimi、GLM、DeepSeek harness、通义/千问系 vs Codex、Claude Code、Cursor、Gemini CLI、Cline 等），没有任何单一项目能全部适配——这恰是开源的机会：MIT 宽松许可 + 适配器插件架构，让每个 Agent 的用户/厂商都有动力来贡献和长期维护自己的适配器（国内 Agent 厂商甚至可能官方接入，因为这对它们是无成本的差异化卖点）。
3. **agentmemory 的定位差异**：它专注编程 Agent 记忆层且存储封闭；本项目做全领域个人知识库，复用其引擎无法获得 Markdown 事实源，收益有限。

agentmemory 的角色从"潜在引擎"降级为：**Phase 0 的实测对照组 + 采集钩子机制的参考实现**。

### 7.2 开源与社区生态策略

| 要素 | 设计 |
|---|---|
| 许可 | 核心与官方适配器均 MIT（宽松，最大化厂商/社区接入意愿） |
| 架构约定 | **核心与适配器严格分离**：核心只依赖"适配器接口"（采集源接口 + MCP 接入），任何 Agent 适配 = 实现一个 adapter 包，独立仓库/目录、独立发版 |
| 首发官方适配器 | 自用优先：Claude Code、Cursor（个人日常工具），各做一个高质量样板，作为社区贡献的模板 |
| 社区适配目标 | 国内：Kimi、GLM、DeepSeek harness、通义系；国外：Codex CLI、Gemini CLI、Cline、Aider、Warp 等 |
| 贡献门槛 | 适配器贡献指南 + adapter 模板仓库 + 采样数据格式文档；适配器测试用统一 fixture（模拟会话样本）**且必须附该工具真实会话样本的回归测试**（吸取 lore 教训：仅靠 schema fixture 的提取器未经真实数据验证，标注"未经真实数据验证"的适配器在 README 中降级展示） |
| 命名与品牌 | 尽早定名、注册 org、占位 npm/PyPI 包名（避免生态起名冲突） |

> 注：适配器分裂风险（各 Agent 会话格式无标准、随版本漂移）通过"核心只认统一中间格式（Unified Session Schema）+ 适配器负责格式转换"来隔离——格式漂移只影响单个适配器，核心稳定。

### Phase 0 — 竞品实测 + 核心原型（1–2 周）

- 安装并日常使用 agentmemory（`npx -y @agentmemory/agentmemory`），作为对照组
- **实测记录**（不信 README 自报数据）：自动采集漏采率、检索命中质量、非编程会话（生活/决策类）的加工效果、Windows 体验——结论作为自研设计的输入（学其钩子机制，避其封闭存储）
- 最简自研 MCP server + `knowledge/` 目录，`save` / `search`（FTS5 全文）在 ≥2 个 Agent 中跑通
- **产出：实测报告（差距机会清单）+ 可用原型**
- 退出标准：连续一周每天自然使用原型

### Phase 1 — MVP：全领域加工 + Markdown 事实源（1–2 月）

- LLM 加工流水线：**全领域**抽取（偏好/事实/决策/经验）→ 去重合并 → 分类打标（生活/编程/项目…）→ 写入 Markdown（含 frontmatter）
- Markdown 为事实源：条目粒度、目录结构（参考 memofs `.memofs/` 分层：核心事实/时序笔记/事件流/归档分离）、Obsidian 兼容性设计（含 5.3.1 产物仓库分离）
- 混合检索（FTS5 + 向量，含返回 token 预算与懒加载，见 5.4）
- 项目指纹与路径注册表（5.3.2，跨设备项目身份的地基）
- 记忆条目审查 UI（Web 或 TUI）

### Phase 2 — 跨设备同步（1 月）

- git 同步命令封装（init/pull/push/status）或 Syncthing 配置向导
- 多设备冲突策略（条目粒度 + frontmatter 结构化降低冲突面）；高敏条目（`sensitivity`）同步排除
- 备份与恢复

### Phase 3 — 自动采集 + 开源发布（2–3 月）

- **自研会话采集 watcher**：统一中间格式（Unified Session Schema）+ 适配器架构（7.2），首发 Claude Code、Cursor 两个官方适配器作样板；适配器接口参考 hstry 的 `detect+parse` 模块设计与 lore 的 extractors 包结构
- 浏览器扩展采集网页对话（ChatGPT/Claude/Kimi 网页端，参考 hstry MV3 方案），打通全领域采集的第二通道
- 双通道去重（会话指纹）
- 记忆生命周期管理：过期、冲突消解（supersedes）、定期压缩合并、分层（热/冷）；**记忆 Linter**（检测断链引用、矛盾断言、失效来源，可跑 CI，参考 memofs）；`why <id>` 来源回溯（lineage）
- **开源发布**：定名、MIT License、GitHub org、适配器贡献指南与模板仓库、统一 fixture
- 时间线视图：记忆的产生与失效轨迹

### Phase 4 — 生态与技能库（持续）

- 社区适配扩张：Kimi、GLM、DeepSeek harness、Codex、Gemini CLI 等（优先合并社区 PR，厂商官方接入优先响应）
- 参考 Anthropic Agent Skills（SKILL.md）格式，把高频记忆蒸馏为技能文件（流程、模板、踩坑经验）；`get_skill` 工具暴露给所有 Agent
- MCP 调用率观测与工具描述迭代闭环（5.4）
- 技能市场/分享（可选，社区方向）

## 8. 关键风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 各工具会话存储格式不稳定、逆向适配易碎 | 高 | 采集器插件化 + 格式版本探测 + 失败降级为"仅 MCP 采集" |
| LLM 加工质量不稳定（漏抽取/幻觉/过度合并） | 高 | 置信度分级 + 用户审查闭环 + 加工 prompt 持续调优（自己是重度用户） |
| 隐私顾虑：敏感对话进入知识库 | 高 | 本地优先 + 隐私过滤规则（黑名单模式）+ 加工模型可全本地 |
| mem0/agentmemory 等竞品快速向"全领域 + Markdown + 跨设备"扩展 | 高 | 加快差异化四要素落地节奏；Markdown 事实源保证用户可随时无损迁出（数据主权即护城河） |
| 全自研战线长，采集/检索工程质量短期追不上成熟竞品 | 高 | 核心只做"够用"的采集与检索，火力集中在竞品没有的 Markdown/全领域/跨设备；agentmemory 钩子机制作参考实现降低设计成本 |
| 开源社区冷启动：适配器没人贡献，自维护压力大 | 中 | 官方先做 2 个高质量样板适配器降低贡献门槛；统一中间格式隔离格式漂移；优先响应国内 Agent 社区（Kimi/GLM/DeepSeek 用户基数大、竞品适配薄弱，是生态切入点） |
| Agent 不愿主动调用 MCP 工具，知识库形同虚设 | 中 | 5.4 的优化组合拳（工具精简 + 被动注入兜底 + 调用率观测闭环），调用率列入核心指标 |
| 记忆膨胀导致检索质量下降 | 中 | 分层记忆（热/冷）、定期压缩合并、标签体系治理 |
| 多设备同步冲突 | 中 | Markdown + git 天然可 diff；条目粒度小、frontmatter 结构化降低冲突面 |

## 9. 成功指标（前 6 个月，自用阶段）

- **留存**：自己连续 30 天每天自然使用（采集零操作）
- **复用率**：每周跨 Agent 检索命中 ≥ 20 次
- **调用率（新增，Phase 3 起）**：Agent 主动调用 `search_memory` 的"应调尽调"比例 ≥ 70%（基于调用日志的人工抽样判定），被动注入（MEMORY-INDEX.md）覆盖核心记忆命中率 ≥ 80%
- **质量**：自动写入记忆的人工审查通过率 ≥ 80%，幻觉率 < 5%
- **成本**：单次会话加工延迟 < 30s，月 API 成本可控（或全本地）

### 10.2 组件复用与重写参考（2026-10 调研新增）

> 详细的组件复用清单（A 直接依赖/B 源码吸收/C 机制参考分级）、许可证合规操作与吸收优先级排序，见配套文档：[参考项目组件复用与许可证风险清单](./参考项目组件复用与许可证风险清单.md)。

四个 MIT 项目，定位各异但各有关键机制值得复用或重写时参考：

| 项目 | 定位 | 与本项目关系 | **重点吸收** |
|---|---|---|---|
| **[memoir](https://github.com/camgitt/memoir)** | 便携式**项目级** Markdown 记忆 + 会话交接（Codex↔Cursor），MCP 工具集 | 部分竞品（项目级 vs 本产品全领域个人级） | ① 会话交接设计（`work setup/resume`：目标+决策+下一步+检查回执跨工具携带）；② 自动采集记录默认 `unverified` 标记、与"已验证"分层——直接补强 5.3 的置信度设计；③ SessionStart hook 注入 ~300 token 简报的 token 预算控制；④ MCP 连接刻意不可执行命令的安全边界 |
| **[lore](https://github.com/DnaMes/lore)** | 本地优先的双工具：10+ AI 工具会话档案库 + 共享 Agent 记忆（Python，SQLite+FTS） | 架构同路人 | ① `extractors`（各工具会话解析器）包结构与本规划"统一中间格式 + 适配器"完全同构，重写适配器层的直接蓝本；② 会话切换器（限流时携上下文切换工具）是记忆之外的好功能参考；③ `--redact` 密钥脱敏（OpenAI/JWT/PEM 正则库）；④ 教训：其 Kimi/Cline 等提取器"仅靠 schema fixture、未经真实数据验证"——适配器必须有真实样本回归测试 |
| **[hstry](https://github.com/byteowlz/hstry)** | Rust 编写的统一 AI 聊天历史库（SQLite） | **关键缺口补齐者** | ① **Chrome MV3 扩展后台同步网页对话**（ChatGPT/Claude/Gemini/Perplexity）——全领域采集（非编程会话）的最优解，本规划此前只考虑文件 watcher，这是重要补充；② SSH 远程同步/搜索其他机器数据库的跨设备方案（与 git 同步互补的轻量选项）；③ 适配器 `detect(path)+parse(path)` TS 模块接口，简洁可借鉴；④ porter 词干化 vs 保留代码分隔符的查询类型自动识别 |
| **[memofs](https://github.com/memo-fs/memofs)** | **文件优先**记忆运行时（`.memofs/` Markdown+JSONL，9+ Agent hook 注入） | **理念最接近的竞品**（file-first 反对 database-first） | ① `.memofs/` 目录结构设计（core/notes/events/graph/archive/snapshots 分层）——本产品 `knowledge/` 目录结构的直接参考；② **记忆 Linter**（CI 检测断链引用、矛盾断言、失效 provenance）——值得纳入生命周期管理；③ `memofs why <id>` 因果 lineage 回溯；④ 源码字节哈希锚定 + 漂移检测（源文件变化自动降权陈旧知识）；⑤ 开源核心+付费云的开源商业模式样本 |

**综合判断**：

1. **差异化空间进一步收窄但未被占领**：memofs 已做 file-first 记忆运行时，hstry 已覆盖网页对话采集与 SSH 跨设备——但四者仍是"编程 Agent 记忆/历史"框架，无一家同时具备"全领域 + Markdown 事实源 + git 级跨设备 + 技能沉淀"完整组合，且 memofs 走 open-core（托管云收费）而非完全 MIT 开放的生态策略，社区适配动力受限。
2. **自研成本显著低于预期**：适配器层可大量参考 lore/hstry 的实现（含国内工具的部分尝试），采集端组合"文件 watcher（本地 Agent）+ 浏览器扩展（网页会话）"双通道即可覆盖全领域，无需从零摸索。
3. **设计吸收清单（并入各章）**：unverified 分层（5.2 条目格式）、网页对话采集通道（5 总体架构采集层）、记忆 Linter 与 lineage（Phase 3 生命周期管理）、目录结构（Phase 1 Markdown 事实源设计）、适配器真实样本回归测试（7.2 贡献门槛）。
